\chapter{Introduction}
\hypertarget{md_docs_2inter-part}{}\label{md_docs_2inter-part}\index{Introduction@{Introduction}}

 Les interruptions sont un outil fondamental dans la communication d’un système avec son environnement. Leur gestion, nécessaire, soulève quelques questions liées notemment au fil d’exécution.\hypertarget{md_docs_2inter-part_autotoc_md44}{}\doxysection{\texorpdfstring{Interruption, exception, code de traitement}{Interruption, exception, code de traitement}}\label{md_docs_2inter-part_autotoc_md44}
Une interruption peut être vue commme la manifestation d’un événement qui va perturber le fil d’exécution en cours sur un processeur. Nous pouvons les classifier en deux catégories


\begin{DoxyItemize}
\item {\bfseries{Les interruptions asynchrones}} (que nous appellerons simplement {\itshape interruptions}) sont le fait d’un élément extérieur au fil d’exécution en cours (une touche du clavier a été manipulée, une carte réseau a reçue une trame, …). Nous parlerons également d’irq (ou {\itshape Interrupt Re\+Quest} pour demande d’interruption).
\item {\bfseries{Les interruptions synchrones}} (que nous appellerons {\itshape exceptions}) sont déclanchées par le processeur lui-\/même comme conséquence de l’exécution (ou de la tentative d’exécution) d’une instruction.
\end{DoxyItemize}

Une interruption, qu’elle soit synchrone ou non, aura pour conséquence l’exécution par le processeur d’un code, appelé {\itshape handler} d’interruption ou isr (pour {\itshape Interrupt Service Routine}). Ce code est en charge de traiter l’interruption.

Notons qu’il est également possible de générer volontairement une interruption dans le code en cours d’exécution grâce à l’instruction assembleur {\ttfamily int n} (qui déclancher l’interruption de vecteur {\ttfamily n}). Nous utiliserons cette option (ajouté au fait que le déclanchement d’une interruption à de sconséquences plus complexes que le “simple” déroutement de l’exécution) pour mettre en place le mécanisme des appels système.\hypertarget{md_docs_2inter-part_autotoc_md45}{}\doxysubsection{\texorpdfstring{Vecteurs d’interruption, table d’interruption}{Vecteurs d’interruption, table d’interruption}}\label{md_docs_2inter-part_autotoc_md45}
Chaque interruption est associée à un {\itshape vecteur} qui va faire office d’identifiant. C’est {\itshape via} ce vecteur que le microprocesseur pourra déterminer où est le code du handler qu’il doit exécuter lorsqu’une interruption est déclanchée.

Concrètement, ce vecteur n’est pas directement l’adresse du handler, mais l’indice dans une table, d’un descripteur du code du handler. Il est ainsi possible d’avoir des descripteurs plus riches, qui ne sont pas réduits simplement à l’adresse du code.\hypertarget{md_docs_2inter-part_autotoc_md46}{}\doxysubsubsection{\texorpdfstring{La table d’interruptions x86}{La table d’interruptions x86}}\label{md_docs_2inter-part_autotoc_md46}
Sur l’architecture x86, cette table est appelée idt (pour {\itshape Interrupt Descriptor Table}) ; elle contient au maximum 256 descripteurs. Chacun de ces descripteurs est constitué de 8 octets qui décrivent l’adresse du handler, le niveau de privilège requis, le type d’interruption, etc …

Cette table peut se situer n’importe où en mémoire, c’est au système d’exploitation de l’initialiser et d’informer le microprocesseur de l’adresse à laquelle elle se trouve et de sa taille. Le noyau utilise pour cela l’instruction {\ttfamily lidt}.\hypertarget{md_docs_2inter-part_autotoc_md47}{}\doxysubsection{\texorpdfstring{Les interruptions}{Les interruptions}}\label{md_docs_2inter-part_autotoc_md47}
\hypertarget{md_docs_2inter-part_autotoc_md48}{}\doxysubsection{\texorpdfstring{Les exceptions}{Les exceptions}}\label{md_docs_2inter-part_autotoc_md48}
Les exceptions permettent donc de traiter un comportement erroné du code en cours d’exécution (une tentative de division par zéro, un accès à une zone mémoire protégée, …).

Elles sont traitées par le système de la même façon que les interruptions déclanchées par du matériel. L’essentiel de ce qui est dit ici pour les interruptions l’est donc en particulier pour les exceptions.\hypertarget{md_docs_2inter-part_autotoc_md49}{}\doxysubsubsection{\texorpdfstring{Les exceptions x86}{Les exceptions x86}}\label{md_docs_2inter-part_autotoc_md49}
Sur les processeurs Intel, les 32 premiers vecteurs sont attribués aux exceptions.\hypertarget{md_docs_2inter-part_autotoc_md50}{}\doxysubsection{\texorpdfstring{Les handlers d’interruption}{Les handlers d’interruption}}\label{md_docs_2inter-part_autotoc_md50}
Quelle que soit la nature de l’interruption, lorsqu’elle se produit, un code spécifique (le “handler”) est exécuté par le processeur. Ce code doit donc effectuer certaines tâches


\begin{DoxyItemize}
\item Sauvegarder l’état du microprocesseur de sorte à pouvoir ensuite reprendre l’activité qu’il menait.
\item Intéragir éventuellement avec le matériel responsable de cette interruption pour le prévenir que le traitement est en cours.
\item Réaliser (ou reporter à un avenir proche) les opérations nécessaires suite à l’interruption \+: recevoir une trame sur une interface réseau par exemple.
\item Restaurer l’état du microprocesseur qui reprendra où il en était avant l’interruption.
\end{DoxyItemize}\hypertarget{md_docs_2inter-part_autotoc_md51}{}\doxysubsection{\texorpdfstring{Le traitement différé}{Le traitement différé}}\label{md_docs_2inter-part_autotoc_md51}
\hypertarget{md_docs_2inter-part_autotoc_md52}{}\doxysubsection{\texorpdfstring{Masquage}{Masquage}}\label{md_docs_2inter-part_autotoc_md52}
Une interruption peut éventuellement être {\itshape masquée}, ce qui signifie qu’elle ne sera pas délivrée au processeur, qui ne s’appercevra donc pas qu’un événement s’est produit. Mais le masquage d’une interruption n’empêche évidemment pas cet événement d’arriver !\hypertarget{md_docs_2inter-part_autotoc_md53}{}\doxysubsection{\texorpdfstring{Traitement d’une interruption \+: partie haute et partie basse}{Traitement d’une interruption : partie haute et partie basse}}\label{md_docs_2inter-part_autotoc_md53}
Le traitement d’une interruption est donc en partie réalisé dans un {\itshape handler}. Pour des raisons de simplicité, nous allons écrire ces handlers en assembleur mais nous y utiliserons dès que possible des fonctions C.

Il est fondamental de comprendre que lorsqu’une interruption est prise en compte par le processeur, le code qu’il était en train d’exécuté est {\itshape interrompu} (surprise ?) pour exécuter le {\itshape handler}. Lorsque l’exécution de ce dernier s’achève, l’exécution du code interrompu reprend son cours. Il est donc crucial que le {\itshape handler} ne réalise pas de modification du système qui rendrait cette exécution incohérente (par exemple en supprimant une ressource que ce code s’appétait à utiliser après s’être assuré de sa disponibilité).

Un autre élément fondamental est le fait que lorsqu’un handler s’exécute, les interruptions ont inhibées et ne peuvent donc plus être prises en compte\mbox{[}1\mbox{]}.\hypertarget{md_docs_2inter-part_autotoc_md54}{}\doxysection{\texorpdfstring{Le $<$em$>$\+Programmable Interrupt Controller$<$/em$>$}{Le <em>Programmable Interrupt Controller</em>}}\label{md_docs_2inter-part_autotoc_md54}
Les interruptions peuvent arriver depuis plusieurs sources. Celles provenant de périphériques (clavier, cartes réseau, …) sont éventuellement acheminées au travers de circuits spécialisés appelés pic.

Le pic est donc un circuit électronique permettant de gérer les irq provenant de l’environnement afin de les délivrer au processeur (c’est en fait une fonction du {\itshape southbridge}).

Je ne m’étalerai pas ici sur les différents types de pic ni sur leur fonctionnement. Ce qu’il est nécessaire de comprendre, c’est qu’il existe donc un circuit avec lequel le processeur va devoir dialoguer pour une partie de la gestion des interruptions.

Nous verrons plus loin que ManuX gère le 8259A qui est un pic conçu par Intel.\hypertarget{md_docs_2inter-part_autotoc_md55}{}\doxysubsection{\texorpdfstring{Le pic Intel 8259A}{Le pic Intel 8259A}}\label{md_docs_2inter-part_autotoc_md55}
Sur un (vieux) pc, le pic est un circuit Intel 8259A. Ce circuit permet de gérer 8 types d’interruptions et on en utilise plusieurs en cascade pour les additionner. Nous supposerons ici qu’il y en a deux, le pic 2 étant derrière le pic 1 (en “cascade”) pour un total de 15 interruptions.

Ce circuit, donc on peut trouver la spécification\mbox{[}2\mbox{]} se programme au travers de deux registres

Le registre de commande ~\newline
 accessible par le port 0x20 pour le circuit maître et 0xa0 pour le circuit esclave ;

Le registre de données ~\newline
 accessible par le port 0x21 pour le circuit maître et 0xa1 pour le circuit esclave.

Une phase d’initialisation est nécessaire afin de configurer correctement ces circuits.\hypertarget{md_docs_2inter-part_autotoc_md56}{}\doxysection{\texorpdfstring{Définition des handlers}{Définition des handlers}}\label{md_docs_2inter-part_autotoc_md56}
Sur le 386, une table (l’idt pour {\itshape Interrupt Descriptor Table}) définit le comportement à adopter pour chacune des 256 interruptions et exceptionns. Cette table est enregistrée grâce à l’instruction {\ttfamily lidt}.

Cette table contient des entrées de trois types différents

Interrupt Gate ~\newline


Trap Gate Descriptor ~\newline


Task Gate Descriptor ~\newline

Observons ici comment tout cela est mis en place dans ManuX.

Nous ne pouvons pas faire l’impasse sur un peu d’assembleur, si bien que les fonctions “bas niveau” seront implantées dans les fichiers {\ttfamily manux/i386/inter\+Bas\+Niveau.\+h} et {\ttfamily i386/inter\+Bas\+Niveau.\+nasm}. Tout le reste sera en C dans {\ttfamily \doxylink{include_2manux_2interruptions_8h}{manux/interruptions.\+h}} et {\ttfamily \doxylink{interruptions_8c}{i386/interruptions.\+c}}.

Nous allons traiter séparément les trois types d’interruptions suivants \+:


\begin{DoxyItemize}
\item les exceptions seront gérées ensemble via une fonction commune \+: {\ttfamily \doxylink{interruptions_8c_ab8ede39e92b659dc067644ea9a5d43ba}{gestion\+Exception()}} ;
\item les IRQ seront traitées par une fonction commune, liée au PIC utilisé ;
\item les exceptions logicielles seront elles aussi regroupées dans une seule fonction de traitement \+: {\ttfamily \doxylink{interruptions_8c_a1c93a6acba307c0339b7208e55cf9c29}{gestion\+Interruption()}}.
\end{DoxyItemize}

Dans les trois cas, la stratégie sera la même \+:


\begin{DoxyItemize}
\item Nous allons définir en assembleur une fonction de traitement spécifique à chaque interruption. J’appellerai par la suite ces fonctions des {\itshape handlers d’interrruption}. Un handler d’interruption sera chargé d’invoquer une fonction d’aiguillage, écrite en C.
\item Nous allons ensuite définir en C une fonction commune d’aguillage pour chaque type ({\ttfamily \doxylink{interruptions_8c_ab8ede39e92b659dc067644ea9a5d43ba}{gestion\+Exception()}} pour les exceptions par exemple). Le rôle de cette fonction sera d’invoquer la fonction C chargée du traitement de l’interruption qui aura été déclenchée.
\item Nous construirons enfin un tableau indexé par le numéro d’interruption et contenant un pointeur sur la fonction C de chaque interruption que l’on souhaite traiter spécifiquement.
\end{DoxyItemize}

Nous allons observer à titre d’exemple les fonctions de gestion des exceptions. Certaines exceptions empilent un code d’erreur de 32 bits et d’autres ne le font pas. Comme nous faisons le choix de passer par une fonction unique d’aiguillage, nous allons empiler une valeur nulle sur 32 bits pour les exceptions qui n’utilisent pas de code d’erreur.

Voici par exemple comment est écrit le gestionnaire bas niveau de l’exception 0 (“division par zéro”) qui n’empile pas de code d’erreur \+: \begin{DoxyVerb}{language=nasm}
golbal stubHandlerExceptionDivO
stubHandlerExceptionDivO :      ; Exception "division par zero"
       push dword 0x0           ; On empile un "code"
       push dword 0x0           ; On empile le numero de l'exception
       pushad                   ; sauvegarde des registres
       call gestionException    ; appel de la fonction d'aiguillage
       popad                    ; restauration des registres
       add esp, 0x08            ; on "depile" le code et le numero
       iret
\end{DoxyVerb}
 Et voici maintenant le code du gestionnaire bas niveau de l’exception 0x0a (“\+TSS invalde”) qui empile l’indice du TSS en erreur \+: \begin{DoxyVerb}{language=nasm}
global stubHandlerExceptionInvalidTSS
stubHandlerExceptionInvalidTSS :
       push dword 0x0a          ; On empile le numero de l'exception
       pushad                   ; sauvegarde des registres
       call gestionException    ; appel de la fonction d'aiguillage
       popad                    ; restauration des registres
       add esp, 0x08            ; on "depile" le code et le numero
       iret
\end{DoxyVerb}

Voici par exemple à quoi ressemble le handler généré pour l’\+IRQ 0 \+: \begin{DoxyVerb}stubHandlerIRQ0 :
   push dword 0            ; On empile le numero de l'IRQ

handlerIRQ :
   pusha                   ; On empile les registres
   call MANUX_HANDLER_IRQ  ; On appelle la fonction d'aiguillage
   popa                    ; On depile les registres
   add esp, 4              ; Depile le numero d'IRQ
   iret
\end{DoxyVerb}

 Regardons maintenant à quoi ressemblent les fonctions d’aiguillage.\hypertarget{md_docs_2inter-part_autotoc_md62}{}\doxysubsection{\texorpdfstring{Les fonctions d’aiguillage}{Les fonctions d’aiguillage}}\label{md_docs_2inter-part_autotoc_md62}
Les fonctions d’aiguillage sont extrèmement simples \+: on utilise un tableau dans lequel sont stoquées les pointeurs de fonction de chaque interruption. La fonction d’aiguillage se contente donc d’invoquer la fonction stoquée à l’indice correspondant.

Pour les IRQ , ce travail est réalisé par une fonction spécifique au pilote du PIC .\hypertarget{md_docs_2inter-part_autotoc_md63}{}\doxysubsection{\texorpdfstring{Définition d’un handler en C}{Définition d’un handler en C}}\label{md_docs_2inter-part_autotoc_md63}

            uint32_t eip, uint32_t cs, uint32_t eFlags)
{

 Nous la définissons avec les paramètres qui sont, dans l’ordre inverse, les valeurs empilées par le processeur lors de l’interruption puis par le handler “bas niveau” décrit ci-\/desssus.

La structure {\ttfamily Tous\+Registres}, décrite dans {\ttfamily manux/types.\+h}, permet de manipuler simplement l’ensemble des registres.\hypertarget{md_docs_2inter-part_autotoc_md64}{}\doxysubsection{\texorpdfstring{Insertion d’un handler dans l’idt}{Insertion d’un handler dans l’idt}}\label{md_docs_2inter-part_autotoc_md64}

 * Affectation du handler de l'interruption i

{
   idt[i].itg.offsetFaible = ((uint32_t)handler & 0xFFFF);
   idt[i].itg.offsetFort = ((uint32_t)handler >> 16);

 Elle sera donc appelée par la procédure d’initialisation de l’idt pour chacune des interruptions.\hypertarget{md_docs_2inter-part_autotoc_md65}{}\doxysubsection{\texorpdfstring{Initialisation de la table IDT}{Initialisation de la table IDT}}\label{md_docs_2inter-part_autotoc_md65}

 Nous pouvons enfin définir les handlers plus spécifiques \begin{DoxyVerb}{}

   positionnerHandlerInterruption(idt, intTimer, stubHandlerTimer);

   /* Le handler du clavier */
   positionnerHandlerInterruption(idt, intClavier, stubHandlerClavier);

 \hypertarget{md_docs_2inter-part_autotoc_md66}{}\doxysubsection{\texorpdfstring{Gestion du pic Intel 8259a dans ManuX}{Gestion du pic Intel 8259a dans ManuX}}\label{md_docs_2inter-part_autotoc_md66}
Ce circuit est géré au travers de fonctions définies dans {\ttfamily \doxylink{manux_2intel-8259a_8h}{include/manux/intel-\/8259a.\+h}} et implantées dans {\ttfamily \doxylink{intel-8259a_8c}{i386/intel-\/8259a.\+c}}.

L’objectif est assez simple \+: fournir (aux drivers des matériels utilisant un mécanisme d’interruption) une interface générique, c’est-\/à-\/dire indépendante du pic utilisé. Nous allons donc définir quelques fonctions de base permettant à ces drivers de s’interfacer avec le système d’interruption. Si on souhaite utiliser un autre circuit pic (par exemple un apic), il “suffira” de réécrire ces fonctions, il n’y aura pas besoin de modifier le code des nombreux drivers (au moins deux, rendez-\/vous compte du boulot !) qui l’utilisent.

Le principe général consiste à définir un handler d’interruption unique qui va prendre en charge toutes les interruptions générées au travers du pic. Ce handler traitera les aspects spécifiques au pic puis invoquera le handler de chacun des “clients” c’est-\/à-\/dire des drivers des matériels qui sont à la source des interrruptions.

Décrivons les fonctions principales. Vous retrouverez leur code dans {\ttfamily \doxylink{intel-8259a_8c}{i386/intel-\/8259a.\+c}}.\hypertarget{md_docs_2inter-part_autotoc_md67}{}\doxyparagraph{\texorpdfstring{$<$tt$>$i8259a\+Init$<$/tt$>$}{<tt>i8259aInit</tt>}}\label{md_docs_2inter-part_autotoc_md67}
